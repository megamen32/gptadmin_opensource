# Обслуживание GPTAdmin Node через его командный исполнитель

Нода включает командный исполнитель из библиотеки `go-shellmcp/runtime`;
отдельный рабочий сервис ShellMCP для этого не нужен.

Запущенная команда работает внутри systemd cgroup своего исполнителя. Отдельная
группа процессов не выводит её из этого cgroup. Поэтому последовательность
`systemctl stop <свой сервис>; ...; systemctl start <свой сервис>` может
уничтожить управляющую команду до обратного запуска. `Restart=always` не
восстанавливает сервис после явной команды `stop`.

Linux-исполнитель отклоняет распознанные прямые команды остановки своего
сервиса до запуска процесса, включая `sudo systemctl`, абсолютные пути и списки
команд. Проверка относится к `cmd` и `argv`. Чтение состояния своего сервиса
и управление другими сервисами остаются доступны. Это защита от ошибки
оператора; произвольный код внутри Python, стороннего скрипта или root-процесса
не является изолированной средой и может обойти такую проверку.
Для известного локального stdio-сервера `PtyMcp` (`pty-mcp`) тот же валидатор
проверяет `terminal_spawn` с прямым argv или `bash/sh -c/-lc` до передачи
дочернему MCP. Ввод `terminal_write` может идти в SSH, редактор или другую
программу; он не интерпретируется как локальная команда. Самоостановка через
интерактивный ввод и произвольные вложенные программы не покрыта guard.

Полную операцию обслуживания запускайте из native shell либо в отдельном
systemd-сервисе. Для установленного Node используйте существующий manager
с проверенным пакетом и фактически прочитанной ревизией:

```bash
sudo systemd-run --unit=gptadmin-maintenance-<уникальный-id> --collect \
  /usr/bin/python3 /usr/local/lib/gptadmin/gptadmin_node_manage.py update \
  --name primary --package /absolute/path/gptadmin-node-linux-amd64.tar.gz \
  --expected-revision <полная-текущая-ревизия>
```

Перед запуском нужны действующее разрешение на выпуск, проектная release lease
и проверка пакета. Отдельный unit меняет только место исполнения: проверки
manager, сохранение состояния, контроль ревизии и восстановление при ошибке
сохраняются.

Ответ `systemd-run` подтверждает создание операции. Её результат проверяйте по
`systemctl show <unit> -p Result -p ExecMainStatus`, журналу
`journalctl -u <unit>` и установленному `/version`. Не повторяйте принятую
операцию после потери соединения, пока не установлен её исход. В конце
проверьте обычную безопасную команду через публичный MCP.
После `--collect` завершённый unit может быть выгружен; в этом случае
используйте его журнал и фактическое состояние установленного сервиса.

Проверка на настоящем исполняемом файле и одноразовых systemd-сервисах:

```bash
sudo python3 tests/e2e/self_service_control_real.py \
  --shellmcp-binary /absolute/path/bin/shellmcp \
  --expected-commit <ревизия-этого-пакета> \
  --workdir /absolute/path/.tmp/self-service-qa-<уникальный-id>
```

Она проверяет отказ до побочных действий, доступность чтения и другого сервиса,
а затем настоящий перезапуск тестового исполнителя из отдельного unit.
Боевой GPTAdmin эта проверка не останавливает.

Для объединённой Node и исходного пути через настоящий PtyMcp:

```bash
sudo python3 tests/e2e/node_self_service_control_real.py \
  --node-binary /absolute/path/bin/gptadmin-node \
  --expected-commit <ревизия-этого-пакета> \
  --pty-mcp-executable /absolute/path/pty-mcp \
  --workdir /absolute/path/.tmp/node-pty-qa-<уникальный-id>
```

## Атрибуция выполнения

Hub сохраняет проверенного клиента вместе с существующей задачей и передаёт
его исполнителю. До запуска локальной команды или передачи child-вызова
исполнитель записывает и синхронизирует журнал `execution-audit.jsonl` в
каталоге identity, либо по явно заданному `SHELLMCP_AUDIT_LOG`. Новый файл
создаётся с правами `0600`; при недоступном журнале действие отклоняется до
выполнения. Неудачная запись после старта помечается отдельно: процесс уже
запущен, повторять операцию автоматически нельзя.

Запись связывает task/trace, проверенного клиента, версию сборки, PID/PPID
исполнителя, его cgroup и ограниченную цепочку предков. Для локальной shell
команды после старта добавляется PID/PGID. Для child MCP записывается наблюдаемый
stdio PID, если он известен; PID терминала не выдумывается. Команда и входные
данные представлены SHA-256, без argv, stdin, окружения и секретов. Сырой MCP
session ID также заменён хешем. Журнал сохраняется при перезапуске.
Очистка хранилища сохраняет журнал вместе с обязательными квитанциями даже
при превышении лимита; превышение учитывается в существующих storage counters.
Удалённый или подменённый путь журнала считается ошибкой durable audit,
а синхронизация старого открытого дескриптора не подтверждает сохранность файла.

Клиент может передать диагностические `X-GptAdmin-Harness` и
`X-GptAdmin-Native-Session-Id`. Они строго ограничены форматом и сохраняются
как недоверенные hints, не влияющие на права. `client_declared` означает только
заявленный клиентом ID, `not_supplied` — клиент не передал ID, `not_recorded` —
его не было в старой записи. По client ID или MCP session ID нельзя восстановить
неизвестный родительский чат.
