# Единый GPTAdmin Node и отказоустойчивый доступ

Статус: проект решения, 2026-09-09. Это не заявление о завершённой миграции.
Исходное состояние отревьюено и отправлено в main: `cb33748`.

Первый срез реализован в рабочем дереве: `go-hub/cmd/gptadmin-node` запускает
hub и исполнитель в одном процессе. Исполнитель использует прежнюю durable
queue через собственный listener узла, а не отдельный relay. Реальная
канарейка `tests/e2e/node/run.py` выполнила команду при `HUB_URL` на
недоступном порту, проверила файл и API-result, отказ 401 без авторизации и
SIGTERM (exit 0, 1.117 секунды). Это локальный candidate, не rollout fleet.
Self-update встроенного shell отключён: обновлять его отдельным shell-архивом
нельзя, иначе он заменит весь node binary. Unified release updater ещё нужен.

Независимый Tester дополнительно подтвердил SQLite receipt после shutdown,
остановку активной группы `sleep 30` и отсутствие отложенной записи через
32 секунды. Локальный executor использует неперсистентный credential,
доступный только компонентам этого процесса; общий fleet credential не
даёт доступ к его очереди и записи результата. SIGTERM отменяет активные
локальные команды с сохранением результата/неотправленного receipt, затем
закрывает router. Это не обещание продолжения команды после остановки узла.

Воспроизводимая проверка из корня проекта (всё временное остаётся в `.tmp`):

```sh
mkdir -p .tmp/node-build
(cd go-hub && GOTMPDIR="$PWD/../.tmp/node-build" go build -o ../.tmp/node-build/gptadmin-node ./cmd/gptadmin-node)
python3 tests/e2e/node/run.py .tmp/node-build/gptadmin-node
```

У обычного запуска сохраняется текущая настройка hub (`GPTADMIN_CONFIG_DIR`,
`GPTADMIN_HUB_HOST`, `GPTADMIN_HUB_PORT`, credentials). Legacy SSH backend
игнорируется для встроенного исполнителя: self-target всегда означает эту
машину. Отдельные пути shell identity/spool поддерживаются при миграции.

## Результат для владельца

Любая установленная копия GPTAdmin умеет выполнять команды на своей машине,
принимать клиентское подключение и маршрутизировать запросы к доступным узлам.
Падение домашнего сервера, одного публичного VPS или туннельного провайдера
не должно закрывать доступ ко всем остальным живым машинам.

Потерянную машину нельзя исполнить на другом сервере: её процессы, устройства
и файлы остаются на ней. Резервируется доступ и управление живыми узлами,
а не физическое существование выключенного сервера.

## Два варианта стабильного входа

| Вариант | Минимальная поставка | Плюсы | Ограничения |
|---|---|---|---|
| Собственный домен, независимые входы | Два публичных узла в разных местах, TLS на обоих, проверяемое DNS-переключение; список адресов в native client | Переносимость между провайдерами; прямой доступ к каждому узлу | DNS-кэш даёт задержку; сам DNS остаётся зависимостью; существующее соединение не переезжает |
| Managed edge/tunnel | Один собственный hostname, несколько коннекторов/пулов к разным узлам | Проще для NAT; endpoint стабилен внутри провайдера | Зависимость от edge; replica tunnel не равна проверке работоспособности приложения; переход между провайдерами требует DNS или поддержки клиента |

Рекомендуемый базовый путь — первый; tunnel является дополнительным способом
достижимости, а не обязательной основой продукта. При отсутствии публичного
адреса владелец может выбрать второй. Не строим собственный anycast/BGP.

Оценка после проверки доступов: прототип первого входа и отключения одного
узла 30–60 минут; интеграция с реальным DNS либо уже настроенным tunnel —
отдельный цикл после инвентаризации. Это не оценка всей миграции и не обещание
одинаковых возможностей бесплатных тарифов.

Канарейка обоих вариантов: клиент сохраняет тот же hostname, один origin
недоступен, новое авторизованное подключение выполняет безвредную команду
на живом узле. Измеряется время восстановления, а не только HTTP health.

Отброшены: один центральный балансировщик на домашнем сервере; надежда на
обычный DNS round-robin как на health-checked failover; автоматическое
переключение провайдерских URL с обещанием неизменного адреса.

## DNS и сертификаты

Let’s Encrypt выдаёт бесплатные сертификаты непосредственно на IPv4/IPv6,
срок действия 160 часов. Для них нужно автоматическое продление и реально
доступная ACME-проверка. IP-сертификат не переносит IP между провайдерами.
Источник: [Let’s Encrypt, 2026-01-15](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability.html).

Поддомен DDNS может дать имя, но не устраняет зависимость от владельца DDNS.
Для переносимого пользовательского адреса нужен собственный домен с доступом
к DNS. Сертификаты для него выдаются бесплатно отдельно на входных узлах;
единый private key TLS копировать необязательно.

Cloudflare Tunnel поддерживает несколько replicas; они повышают доступность
соединения, но application-aware failover требует дополнительной проверки
origin либо Load Balancing. [Документация](https://developers.cloudflare.com/tunnel/configuration/).
ngrok поддерживает endpoint pooling и географическое распределение;
доступность нужного custom domain и функций зависит от выбранного плана.
[Документация](https://ngrok.com/docs/gateway/domains/global-load-balancer).

У single-URL клиента, например внешнего OAuth/MCP потребителя, fallback-list
не появляется от изменения сервера. Для него обязательно проверяется
переподключение через стабильный DNS/edge hostname. Native клиент может
дополнительно выбирать из сохранённых независимых endpoint-ов.

## Одинаковый узел, разные ресурсы

Один процесс `gptadmin-node`, один публичный адрес и единая служба обновления.
Внутри используются действующие hub и shell реализации. Старые CLI/имена
служб остаются совместимыми на период миграции; их удаляют после canary,
а не одновременно с первым запуском нового бинарника.

Первый исполняемый срез сохраняет только существующую очередь: локальный
shell polling направлен к своему hub независимо от внешнего `HUB_URL`.
Собственная identity закрепляется до открытия consumer path; входящие
регистрации с тем же именем и другой identity не должны её заменять.

Реализована явная маршрутизация между такими узлами:
`GPTADMIN_NODE_PEERS='{"shell:nodeB":"https://node-b.example"}'` на узле A.
REST `/mcp-relay/call` и MCP `execute` передают исходный запрос и Bearer узлу B;
он сам проверяет права, выполняет задание и сохраняет receipt. Локальная
identity имеет приоритет над маршрутом. Разрешён один переход без HTTP redirect
и автоматического повтора потенциально доставленной команды.

Реальная двухпроцессная канарейка проверяет команду A→B, остановку A, прежний
receipt напрямую B, отсутствие второго side effect при том же idempotency key,
новую команду напрямую B и отказ без авторизации. MCP-сценарий использует
обычный managed bearer, auth snapshot и проверяемый HTTPS с закреплённым IP.
Через тот же вход A можно повторно читать receipt, передав `owner_target`,
равный исходному `execute.target`. Автоматического поиска jobs по остальным
узлам нет. REST receipt по-прежнему читается у владельца. Срок существующей
дедупликации (15 минут) не изменён. Этот тест не доказывает неизменность
публичного адреса при аварии; см. [контракт peer routing](NODE_PEER_ROUTING.md).

Узел содержит:

- собственную устойчивую identity и локальный исполнитель;
- MCP/API и текущую авторизацию;
- peer registry с несколькими достижимыми endpoint-ами каждого узла;
- маршрутизацию, локальную очередь и проверяемые receipts выполнения;
- реплику минимального состояния управления и ограниченный кэш;
- выбранный способ публичного входа: direct TLS, reverse proxy или tunnel.

Статичный IP/URL делает узел кандидатом на публичный вход, но не выдаёт ему
права. Нужны enrollment существующим механизмом доверия, подтверждение
достижимости снаружи, работоспособности авторизации и свежести control state.
LAN-адрес сам по себе не означает достижимость из Интернета.

У всех узлов одинаковый код. `ingress`, `replica`, `executor`, `voter` —
способности и настройки размещения, а не разные продукты hub/shell.
Маленький узел не обязан хранить историю остальных или быть голосующим.

Физическая топология — несколько входов и связи между peers. Звезда с одним
обязательным центром сохраняет исходную точку отказа. Исходящие подключения
NAT-узла должны доходить минимум до двух независимых входов.

Выбор топологии — конфигурация, а не отдельный код: writer/центр membership,
member с реплицированным снимком или standalone «все знают всех» на статических
`GPTADMIN_NODE_PEERS`. Источник истины один — membership; статические peers
остаются bootstrap-фолбэком, а `discover` показывает активный режим в поле
`mesh.mode`. См. [контракт peer routing](NODE_PEER_ROUTING.md).

## Репликация по смыслу данных

| Данные | Где хранятся | Частота и поведение |
|---|---|---|
| Identity, доверенные узлы, действующие профили/права, revocations, конфигурация маршрутов | На каждом узле, заявленном готовым резервным входом | Изменения сразу; контроль revision/checksum; подтверждение сохранения перед признанием готовности |
| Статусы узлов и доступные маршруты | На каждом узле | Heartbeat и истекающие записи; не переписывать весь снимок при каждом heartbeat |
| Принятые задания, request IDs, дедупликация и итоговый статус | Прежде всего на исполнителе; receipt у входа | Сохранить до выполнения; повторный запрос возвращает тот же результат/статус |
| История и большие результаты | Владелец плюс выбранные узлы с бюджетом | Инкрементально, по запросу или с ограниченной задержкой; TTL/LRU для подтверждённо необязательного кэша |
| Исходники проектов, пользовательские диски, model weights, APK/архивы | По явной политике владельца | Не копируются автоматически для обеспечения доступности управления |

Обязательные credentials для резервного входа передаются существующим
доверенным provisioning/enrollment-путём. Нельзя считать санитизированный
failover JSON достаточным, а затем обходить auth при аварии. Перед изменением
формата необходимо перечислить фактические auth stores, ключи подписи,
OAuth clients/tokens, WebAuthn и issuer/audience, которые нужны текущему клиенту.

Один node_id не заменяется при смене адреса. Peer endpoint не становится
новым OAuth issuer: сохраняется идентичность кластера и контракт client token.
Для другого URL проверяется поддержка MCP resource/audience конкретным клиентом;
одного совпадения JWT signing key недостаточно.

## Бюджет маленькой машины

Сначала измеряются обязательный control state, free disk, filesystem capacity,
RSS реального бинарника и доступная RAM. Размер диска не является оценкой RAM.

Предлагаемый кэш-бюджет по умолчанию:
`min(500 MiB, 5% capacity, max(0, free_bytes - reserve_bytes))`, где резерв
оставляется операционной системе и действующим заданиям. Точное значение
reserve выбирается после замера классов машин и доступно в настройке.
RAM, сеть, частота записи и количество одновременно работающих jobs имеют
отдельные лимиты; tiny-node не держит весь индекс истории в памяти.

Обязательное состояние и непереданные receipts нельзя молча удалять LRU.
Если они не помещаются: удалить необязательный кэш, остановить приём новых
реплик/заданий по бюджету и снять готовность резервного входа с объяснением.
Сохраняется локальный аварийный доступ, насколько позволяет диск.

Частота синхронизации различается по данным: права нельзя синхронизировать
раз в час ради экономии; большие outputs не нужно передавать каждые секунды.
Используются revisions/deltas, ограничение bytes/sec и backoff. Full snapshot
нужен при bootstrap/выпавшей истории, с предварительной проверкой размера.

## Разделение сети и повторное выполнение

Нельзя одновременно обещать мгновенную глобальную revocation и безусловную
работу автономного узла, который не получает revocation. Контракт должен
явно ограничить срок действия ранее подтверждённых прав и аварийный доступ.

Изменения глобальных прав, membership и владельца расписаний требуют
одного согласованного writer/epoch; для автоматической смены writer нужны
три независимых голоса либо внешний witness. Два сервера без witness не
различают потерю связи и смерть соседа. При потере согласования новые
глобальные grants/смена владельца останавливаются, а локальная работа по
действующим ограниченным credentials проверяется отдельно.

Один executor владеет каждым принятым заданием. Timeout после отправки
не доказывает, что команда не выполнилась: новый ingress выясняет состояние
по request_id у того же executor. Неопределённый результат обозначается
явно; запись с побочным эффектом не повторяется на другой машине.
Exactly-once для произвольной shell-команды при crash между side effect
и записью receipt не обещается.

## Последовательность реализации и проверки

1. Единый executable и service lifecycle. Из публичного MCP/API выполнить
   реальную команду на этом же узле без отдельного shellmcp процесса.
2. Второй независимый узел и peer routing. Команда на B доступна через A
   и напрямую через B; отказ A не мешает B. Проверить идентичность target.
3. Полный минимальный control state и auth continuity. Тот же клиент
   переподключается к резервному входу, разрешённая операция проходит,
   запрещённая остаётся запрещённой; проверить restart резервного узла.
4. Независимые ingress и стабильный hostname. Отключить один вход в
   контролируемом canary, проверить новый сеанс и измерить recovery time.
5. Бюджеты и распределение истории. На реальной маленькой машине измерить
   RSS/disk/network, заполнить необязательный кэш до лимита, подтвердить,
   что control state и незавершённые receipts сохранены.
6. Поэтапная миграция существующей fleet с откатом к предыдущему бинарнику
   и формату состояния. Сначала дополнительный узел, последним primary.

Ни один отдельный пункт не переименовывается в завершение всей системы.
Unit-тесты проверяют логику; приёмка использует реальные процессы, сеть,
auth, выполнение команды, restart и контролируемый отказ. Главный доступ
владельца не отключается до доказанного независимого резервного входа.
