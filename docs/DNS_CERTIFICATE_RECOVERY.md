# Восстановление DNS-01 для существующего входа

На 2026-09-09 wildcard `*.t.became.bezrabotnyi.com` указывает на
`185.240.120.152`. На VPN2 и VUSA обнаружен сертификат, истёкший 28 августа.
VUSA также нестабильно доступен из VPN2; обновление сертификата не доказывает
исправление этой сетевой проблемы и не подтверждает готовность failover.

Для восстановления текущего клиентского доступа через существующий валидный
сертификат добавлена точная A-запись
`your-subdomain.t.became.bezrabotnyi.com → 203.0.113.10` через установленный
SpaceWeb MCP. Wildcard остальных tenant-ов не менялся. Это временное направление
конкретного клиента на primary, а не автоматический failover и не официальная
ChatGPT/Codex identity. Удалять override следует только после доказанного TLS,
авторизации и выполнения через резерв.

Действующий SpaceWeb auth hook `/root/certbot-sweb-auth.sh` добавляет TXT через
существующий `swebmimic editTxt`, но ждёт только 30 секунд. Все четыре
авторитетных NS возвращают TTL 600 секунд. Ошибка ACME `Incorrect TXT record`
совместима с кэшированием прежнего RRset; содержимое кэша CA не установлено.
Делегация уже указывает на SpaceWeb, TTL родительской делегации — 172800 секунд.

`scripts/certbot_dns_propagation_hook.sh` оборачивает существующий provider hook:
сначала получает TTL, вызывает hook, затем проверяет текущий challenge на всех
настроенных authoritative NS и выжидает прежний TTL с момента наблюдаемой
сходимости. Каждый challenge проверяется отдельно. При ошибке или timeout
обёртка возвращает ненулевой код. В установленном Certbot manual plugin этот
код только протоколируется: он не гарантирует остановку validation. Успех
выпуска подтверждается ответом CA и выданным сертификатом, а не завершением
hook. Нового DNS API или бесконечного retry-loop нет.
Ошибка DNS-запроса не обнуляет уже наблюдённую сходимость: она не означает
исчезновение записи. Успешный ответ без challenge обнуляет ожидание. Перед
успехом hook всё равно требуется положительный ответ каждого NS.

Значения по умолчанию для существующего SpaceWeb deployment (можно переопределить):

```sh
export DNS_AUTH_HOOK=/root/certbot-sweb-auth.sh
export DNS_AUTHORITIES='ns1.spaceweb.ru ns2.spaceweb.ru ns3.spaceweb.pro ns4.spaceweb.pro'
export DNS_PROPAGATION_TTL=600
export DNS_PROPAGATION_TIMEOUT=1200
```

Путь provider hook и authorities имеют эти значения по умолчанию: certbot
сохраняет путь auth hook, но не окружение исходной оболочки. Для другого
провайдера задайте постоянное окружение службы renewal или отдельный launcher.

Перед одиночным выпуском нужно исключить параллельный запуск текущего
`/root/cert-issue-loop.sh`. В certbot заменяется только `--manual-auth-hook` на
путь установленной обёртки. Два challenge могут занять более 20 минут.
Старая кэшированная делегация этим ожиданием не устраняется. В реальной попытке
09 сентября первый hook достиг timeout; во втором challenge после трёх минут
новый TXT был виден только на одном из четырёх NS. Отдельная успешная выборка
не доказывает непрерывную сходимость всех ответов.

Известный отдельный дефект SpaceWeb cleanup: `info` возвращает имя TXT в поле
`domain`, а существующие клиенты читают `name`; удаление собственных записей не
срабатывает. Не удалять чужие TXT и не угадывать форму delete-запроса. Этот
helper не меняет cleanup API. Старые TXT не заменяют проверку наличия нового.

После выпуска: проверить SAN/срок сертификата, установить в фактически
используемый nginx vhost, выполнить `nginx -t`, reload и внешнюю проверку с
обычной TLS-валидацией. `/version` и OAuth discovery — промежуточные проверки;
готовность резерва требует авторизованного выполнения реальной безопасной
операции при недоступности основного узла.

## Результат восстановления 2026-09-09

Одна реальная попытка certbot получила сертификат до 2026-12-08. Оба hook
достигли timeout; независимый наблюдатель записал 352 проверки: 323 успешных
ответа содержали challenge, 29 DNS-запросов завершились ошибкой. На этой
регрессии исправлено обнуление таймера при недоступном наблюдении; два локальных
теста политики ожидания прошли после воспроизведения ошибки.

Новый сертификат установлен на VPN2 и VUSA. На VUSA дополнительно устранены
переполнение conntrack и конфликт HTTP :443 со stream :443: дублирующий
`sites-enabled/t-gptadmin-public` отключён, действующий путь идёт через TLS
127.0.0.1:8446. До удаления конфликта reload возвращал успех, но nginx оставлял
старый worker. Оба внешних входа теперь проверены с обычной TLS-валидацией.

Четыре authoritative NS вернули точную клиентскую A-запись primary. Реальный
MCP `execute` с существующим managed bearer через VPN2 выполнил `printf` на
`shell:admin-node-100`; обычный DNS-путь вернул тот же job
`bf1a1ea91902178bd56e85cc9953cba6` по тому же idempotency key. Это доказывает
восстановление входа, а не независимость backend от primary.

VUSA по-прежнему маршрутизирует к Hub 1.0.5/9d8a427 и отвергает тот же managed
bearer (401). Автоматическое переключение клиентов на него не включено.
Следующий необходимый этап — совместимое состояние авторизации на независимом
узле; новый сертификат не заменяет этот этап.
