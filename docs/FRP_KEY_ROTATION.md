# Ротация FRP без вывода ключа

Владелец шлюзов и продуктовых FRP-конфигураций — GPTAdmin. Ключи остаются
в защищённых runtime-файлах; в GitHub Actions они не нужны. Нельзя повторно
раздавать опубликованный ключ или возвращать его как штатный rollback.

`tools/frp_key_rotation.py` принимает новый ключ только через stdin. План
содержит абсолютные пути, SHA256 текущих файлов, формат и digest старого ключа.
Поддержаны `token-file`, `env`, `toml`, новый `bezhook-env` и `unit-reference`.
Инвентаризация должна включать активные executable/config/unit и сохранённые
конфиги выключенных клиентов. Выключенные клиенты не включаются при ротации.

До записи проверяются все pins, symlinks и права каталога. Все исходные байты
сохраняются и fsync-ятся в отдельный root-only каталог, затем каждый файл
повторно проверяется и заменяется атомарно с сохранением владельца и прав.
Новые файлы с ключом имеют 0600. Повторное применение старого плана запрещено:
при частичном отказе нужно сверить сохранённый receipt и фактические файлы.
Ключ не передаётся через argv, командный текст, Git, чат или логи.

После записи выполнить штатный `frps verify -c ...` / `frpc verify -c ...`;
вывод сохранять в защищённый файл, наружу выдавать только статус. tokenSource
читается при загрузке конфигурации, поэтому смена файла требует перезапуска
FRP. Последовательно переключать только инвентаризированные FRP units,
сохраняя SSH, Hub, ShellMCP, браузеры и native harness-процессы.

Проверка: новый ключ принимается каждым шлюзом, старый отвергается; существующие
proxy восстанавливаются; harmless реальный MCP-вызов выполняется через туннель.
Прямой HTTP endpoint, обходящий FRP, не доказывает туннель. Неизвестным внешним
подключениям новый ключ не раздаётся. Для недоступных управляемых клиентов
сохранять точный остаток; готовность всех клиентов без их сверки не заявлять.

Бюджет этой операции: метаданные ≤256 MiB/CPU15s/wall30s на хост; максимум
64 файла ≤2 MiB, backup ≤64 MiB; 2 независимых чтения параллельно. Конечный
проверочный frpc запускается на 100, ≤128 MiB/CPU1/tasks32/temp16 MiB/wall20s.
VPS с малым запасом памяти не используются для сборок или новых probe-процессов.
Переключение ≤120s/хост; действующие service caps не повышаются.
