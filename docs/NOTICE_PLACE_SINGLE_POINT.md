# Единая точка Notice Place в AI-клиентах

Notice Place — один MCP-сервер с одним контрактом. Он должен быть **одной
общей точкой** для всех клиентов: единственный работающий сервер
`https://notify.bezrabotnyi.com/mcp` (Streamable HTTP), одно каноническое имя
`noticeplace`, один и тот же список инструментов.

Раньше один и тот же бэкенд был зарегистрирован в клиенте под несколькими
именами (`AskHuman`, `notify`, `NoticePlace`, `noticeplace`), а часть
регистраций поднимала **свой локальный MCP-процесс на клиента** вместо
общего сервера. Теперь:

* каноническая точка — HTTP-эндпойнт общей службы; локальный stdio-процесс
  клиентами больше не используется;
* остальные имена отключаются на месте (`enabled: false`), запись остаётся в
  файле и обратима;
* MCP-поверхность плагина `noticeplace` отключается — плагин остаётся
  носителем SKILL-контракта, а сервер регистрирует только конфиг клиента;
* алиас отключается **только после того**, как каноническая точка доказана
  реальным `initialize` + `tools/list`.

## Команда

```bash
gptadmin notice-place status                      # только чтение
gptadmin notice-place install --dry-run           # план изменений, без записи
gptadmin notice-place install                     # применить
gptadmin notice-place install --refresh-plugin    # свести копии плагина к каноническому пакету

.venv/bin/python scripts/notice_place_endpoint_probe.py   # проба точки: реальный initialize/tools/list
```

`--client` (повторяемый): `opencode`, `codex`, `hermes`, `zcode`, `fast-agent`.

## Каноническая точка

| Параметр | Значение |
|---|---|
| Имя сервера | `noticeplace` |
| Транспорт | Streamable HTTP, `https://notify.bezrabotnyi.com/mcp` |
| Инструментов | 18 (список одинаков для всех клиентов) |
| Учётные данные | уже имеющийся у клиента bearer Notification Center; переносится внутри того же файла конфигурации, не ротируется и не кладётся в новое хранилище |

Локальный stdio-процесс Notice Place на клиенте не используется: ни одна
среда не поднимает собственный MCP-сервер, все работают с одним сервером
службы.

Если у клиента нет своей учётной записи, берётся та, что уже есть в
конфигурации другого клиента этого же хоста (тот же общий bearer). Если её
нет нигде на хосте, каноническая точка не создаётся, алиас остаётся живым и
команда сообщает об этом.

## Безопасность изменения

* Ничего не удаляется: алиас остаётся в файле отключённым.
* Перед каждой записью — резервная копия `<файл>.bak.noticeplace.<время>.<случай>`;
  режим и владелец файла сохраняются.
* JSONC-конфиг с комментариями не переписывается — команда сообщает об отказе.
* Остальные MCP-серверы, провайдеры, разрешения и хуки не затрагиваются.
* Идемпотентность: повторный запуск ничего не пишет и не создаёт новых копий.
* Учётные данные никогда не печатаются: в выводе только имена, флаги, счётчики
  и имена ключей конфигурации.

## Проверенные среды

Два разных уровня доказательства, и они не смешиваются:

* **эффективный набор инструментов harness** — среда сама показывает свой
  список (вызов инструмента в живой сессии, `hermes mcp test`);
* **проба точки** — регистрация, взятая ровно как её использует клиент,
  отвечает настоящим `initialize` + `tools/list` (Streamable HTTP, с
  переносом session id).

Проба точки не доказывает список инструментов harness. Поддерживаемая
команда:

```bash
.venv/bin/python scripts/notice_place_endpoint_probe.py
```

Проба использует `httpx` (уже в зависимостях проекта) и не требует `mcp`.
stdio-регистрация в ней не опрашивается, а помечается как `NOT-PROBED`:
каноническая точка — общий HTTP-эндпойнт.

## Что осталось за пределами проверенного

* **mac-mini-2012.lan — UNKNOWN.** Notice Place не зарегистрирован ни в одной
  среде (`/Users/admin/.codex/config.toml`,
  `/Users/admin/.hermes/config.yaml`): алиасов нет, дублировать нечего.
  Каноническую точку создать нельзя — на хосте нет локального релиза Notice
  Place и нет bearer ни в одном конфиге клиента.
  Следующий шаг: владелец хоста переносит общий bearer Notification Center в
  конфиг клиента (или в переменную окружения клиента) — после этого
  `gptadmin notice-place install` на этом хосте создаёт каноническую точку.
* **node-44: zcode, fast-agent — не установлены.** `~/.zcode/cli/config.json`
  и `~/.fast-agent/fast-agent.yaml` на хосте отсутствуют.
* **ZCode и Fast-Agent — эффективный набор инструментов harness не проверен.**
  У ZCode список MCP доступен только в TUI (`/mcp list`), у Fast-Agent
  `fast-agent auth mcp list` ничего не печатает. Следующий шаг: одна сессия
  каждой среды, которая вызывает `noticeplace_instructions` — как это сделано
  для OpenCode.
* **Codex — эффективный набор инструментов harness не проверен.** Codex-сессия
  не запускалась по условию листа; проверены только конфиг и проекция.
  Следующий шаг: одна сессия Codex, которая вызывает `noticeplace_instructions`.
* **Пакет плагина noticeplace (репозиторий noticeplace) — обновлён.** Проекции
  версии 0.1.0 (`mcp.json`, `mcp.codex.json`) теперь объявляют общий
  Streamable HTTP-эндпойнт с `bearer_token_env_var` и без секрета;
  `opencode.json` и `fast-agent.yaml` оставляют регистрацию клиентскому
  конфигу, потому что эти harness не умеют брать bearer из окружения.
  Версия 0.1.0 — самостоятельный bundle со своим бинарником и своим
  validator-контрактом, он не менялся. Копия пакета в реестре
  agent-harness-fleet устарела (там прежний stdio) — следующий шаг: владелец
  реестра синхронизирует копию с пакетом-источником; `install --refresh-plugin`
  читает пакет из репозитория-владельца и приводит установленные копии к нему.
* **Установщик ask-human в agent-harness-fleet — UNKNOWN.**
  (`plugins/ask-human/scripts/setup_mcp.py`) дописывает в
  `~/.codex/config.toml` блок `[mcp_servers."AskHuman"]`. Он запускается
  вручную и не входит в автоматический путь обновления, но при следующем
  запуске вернёт алиас.
  Минимальная правка для владельца: заменить имя сервера на `noticeplace` и
  URL на `https://notify.bezrabotnyi.com/mcp` — тогда установщик станет тем же
  каноническим писателем, а не источником второго имени.
* **Установленный CLI на MacBook-Pro-User.local** собран до этой правки, так
  что команда `notice-place` появится там только после обновления CLI; правка
  применялась тем же кодом.
* **GPTAdmin-hub: дочерний ShellMCP-регистр `Notify`**
  (`mcp:shell:admin-node-100:Notify`) поднимает локальный stdio-сервер.
  Проверено по фактическому каталогу: инструменты этой точки **не входят** в
  список, видимый агенту (поиск по каталогу для `noticeplace` не даёт ни
  одного результата; `send_message` и `ask_human` отвечают только инструменты
  AgentHerder и Touchpoint). Доступ к ней есть только по явному имени цели.
  Живые webhook-маршруты (`agent-deliver-v1`, `notify-health-diagnosis`,
  `notify-health-remediation`, `agent-wake-v1`, `qa23-forwarder-ready-20261023`)
  идут через этот регистр, поэтому его перенос требует действий на пути
  инцидентов. Блокер: процесс-родитель (`gptadmin-hub.service`) не имеет в
  окружении `NOTIFY_MCP_TOKEN`, а ссылка `${NOTIFY_MCP_TOKEN}` в заголовке
  разрешается только на момент запроса — без переменной в окружении точка не
  пройдёт аутентификацию.
  Подготовленный набор шагов (не выполнялся): добавить в unit
  `gptadmin-hub.service` строку
  `EnvironmentFile=/etc/notification-center.env` (существующее защищённое
  хранилище, значение не копируется), перезапустить hub, затем
  `mcp_manage` upsert регист `Notify` на
  `https://notify.bezrabotnyi.com/mcp` с заголовком
  `Authorization: Bearer ${NOTIFY_MCP_TOKEN}`. Canary: `tools/list` ребёнка
  через hub (18 инструментов) плюс вызов read-only инструмента той же цели.
  Решение о перезапуске hub (16 живых сессий) — за владельцем.
