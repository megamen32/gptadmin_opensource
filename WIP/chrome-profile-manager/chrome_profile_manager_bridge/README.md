# Мост управления расширениями Chrome

Мост использует штатные Chrome management API и native messaging. Исходный MCP предоставляет список, чтение и включение/выключение расширений подключённого профиля. Он не читает страницы, cookies или хранилища и не опрашивает Chrome в фоне.

Подготовка создаёт отдельный каталог расширения и собственную регистрацию native host. Запускать provisioner следует из постоянного установленного каталога: manifest Chrome содержит абсолютный путь к host.py.

```bash
python3 provision.py --profile-id 'имя профиля' --user-data-dir '/абсолютный/каталог/данных/Chrome'
```

Команда выводит каталог расширения. В окне именно нужного профиля Chrome включите режим разработчика на chrome://extensions и выберите этот каталог через «Загрузить распакованное расширение». Это первоначальное действие; команда не изменяет остальные профили. Для каждого профиля используйте отдельное имя и отдельный каталог. Не переносите каталог расширения в другой профиль: уникальный ID сам по себе не удостоверяет профиль, а повторная загрузка может направить запрос не туда. Повторная подготовка того же имени с другим каталогом данных блокируется.

MCP-методы: profile_extensions_list, profile_extension_get, profile_extension_set_enabled. Если ответ Chrome не пришёл в течение 20 секунд или соединение оборвалось после отправки, исход считается неизвестным; host завершает соединение, чтобы запоздавший ответ не был принят за следующую команду. Сначала вызовите profile_extension_get: не повторяйте операцию вслепую. Chrome может запретить включение или потребовать подтверждения, например после расширения разрешений. API management не устанавливает новые расширения и не выполняет обновление или rollback; эти операции доступны отдельно только в ранее проверенном controlled-режиме.

В изолированных Chrome на Linux и macOS проверены подготовка, автоматическое подключение при установке и переключение тестового расширения. На обеих системах дополнительно проверена постоянная установка самого моста через штатный диалог выбора каталога: после перезапуска отдельного тестового браузера Chrome независимо подтвердил его ID, версию и включённое состояние, мост переподключился через onStartup, а заново запущенный тестовый shellmcp получил список через этот мост. После перезапуска тест явно изменяет привязку во временном тестовом каталоге. Для воспроизведения нужны opt-in `CHROME_CONTEXT_QA=1 CHROME_CHOOSER_QA=1 GPTADMIN_CHROME_QA=1`, на Linux отдельный D-Bus-сеанс, на macOS доступ System Events к Accessibility. Установка в обычный профиль и использование нового кода в рабочей регистрации GPTAdmin остаются непроверенными. Один порт удерживает service worker активным без polling. При разрыве мост делает одну отложенную попытку переподключиться; после успешного запроса следующая попытка снова разрешена. Переподключение и ограничение попыток проверены с тестовым native host на обеих системах. Секреты привязок хранятся в закрытом каталоге и не должны передаваться через аргументы команд или в ответы MCP.

Chrome предоставляет origin расширения native host, но не удостоверяет им фактический профиль. Поэтому путь и ID артефакта сами по себе не доказывают, что он загружен в нужном профиле. Один пользователь ОС имеет доступ к своим файлам и процессам; этот механизм не изолирует враждебный код под той же учётной записью.

Источники: https://developer.chrome.com/docs/extensions/reference/api/management и https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging
