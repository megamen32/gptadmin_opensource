# Обнаруженные дефекты

## Потеря ссылки на асинхронную задачу удалённого исполнителя

20 ноября 2026 года запрос через публичный MCP с действующей учётной записью выполнил команду на удалённом участнике, но `mcp.tasks.start` вернул `task_receipt_unavailable`. Все три проверяемые ноды в этот момент работали. В журнале физического владельца сохранились завершённая задача и ожидаемый stdout. Синхронный `mcp.call` на том же участнике вернул результат.

Для воспроизведения подключиться к писателю, вызвать `mcp.inspect` для `shell_exec` другого участника и создать через `mcp.tasks.start` задачу с уникальной строкой вывода. Сверить ошибку клиента с квитанцией у владельца по этой строке. Повторная отправка выполнит команду ещё раз. Место проверки квитанции — `go-hub/internal/hub/code_mode_tasks.go`, метод `createdTask`.

## Штатный мониторинг на сотке и обновление пакета

20 ноября в 06:39 МСК `gptadmin-live-canary.service` на сотке завершился по таймауту чтения результата native MCP на обоих проверяемых адресах. Служба запускается на самой сотке, а `scripts/live_canary.sh` по умолчанию выбирает её же исполнителем. Такой таймаут сам по себе не устанавливает, доступен ли публичный MCP на 44. Для разбора посмотреть журнал службы и сравнить его с результатом команды на 44 через публичный `/mcp`. Состояние ранее отправленной задачи проверять чтением квитанции.

В 06:40 МСК служба `gptadmin-node-autoupdate.service` на сотке вернула `previous manager failure requires verified recovery before automatic retry`. Это защита после предыдущей попытки установки. Состояние воспроизводится чтением журнала службы и сохранённой квитанции установщика. До выяснения результата прежней попытки сохранять эту квитанцию.

## Прямые адреса Mac указывают на устаревшие маршруты

20 ноября клиент на 44 через общий адрес MCP получил контрольную метку и правильную аппаратную модель от Mini, Intel и M1. Все три исходящих WebSocket пережили две перезагрузки сотки. Для прямых HTTPS-адресов действует другая конфигурация. Прямой адрес Mini возвращает `502`, поскольку обратный SSH-туннель на 100 использует прежний адрес Mini. Прямой адрес Intel доступен через туннель на 100. По адресу M1 отвечает писатель. Проверить можно чтением `/version` через соответствующий SNI и сверкой ответа с локальным `/version` того же физического Mac. Затронуты запасные HTTP-маршруты в HAOS и nginx.

## Маршрут к сотке сразу после её возврата

20 ноября 2026 года в первые пять секунд после регистрации восстановленной сотки писатель уже показывал `ready`. Исходящее WebSocket-соединение сотки ещё устанавливалось. Запрос к её запасному HTTPS-адресу вернул ответ, который писатель не смог прочитать как квитанцию. Клиент получил HTTP 502 с неизвестным исходом. Воспроизводится запросом к самой сотке в промежутке между новой регистрацией lease и появлением хоста в `live_connections`. Ответы 44, 88 и Android в это время приходили. При проверке восстановления следует дождаться подключения и получить результат новой команды. Затронуты `go-hub/internal/hub/node_conn.go` и `node_peers.go`.

## Нативная память Node при параллельном Code Mode и отвергнутое лечение

15 ноября 2026 года на node-100 нода держала 19.3 ГиБ приватной анонимной памяти при стабильной Go-куче: 15.13 ГиБ приходились на 69269 анонимных исполняемых отображений, которые нода непрерывно накапливала, и хост достиг подтверждённого ядром истощения памяти. Первой версией причины названо то, что пакет `third_party/qjs` держит compilation cache wazero на весь процесс, поэтому движок с его нативным кодом никогда не освобождается.

Проверка 20 ноября эту версию не подтвердила. Цикл создания и закрытия QJS-рантайма в изоляции не течёт ни в одном варианте: на коде main 200 раундов дают +26 исполняемых отображений, вариант с отдельным кэшем на рантайм — +68. Реальный прирост на production-ноде 15 ноября был 12–48 отображений в минуту, то есть требовал параллельной компиляции одного и того же модуля в общий движок, а не последовательного цикла create/close. Поставленное лечение — отдельный compilation cache на каждый рантайм — добавляет около 250 мс к каждому вызову Code Mode (измерено: 11 мс против 260 мс на раунд) и ломает чувствительный к дедлайну путь: тест `TestCodeModeBlocksWASIHostTimers` в main с этим изменением падает с «module closed with context deadline exceeded». Поэтому изменение в корабельную линию не доставлено, а версия причины в навыке и в карточке инвентаря исправлена.

Для воспроизведения: в `go-hub/third_party/qjs` создать рантайм с функцией-листенером охраны WASI-опроса и лимитом памяти 32 МиБ, как в Code Mode, и закрыть его; затем сверить число анонимных `rwxp` отображений процесса через `/proc/<pid>/smaps`. Место проверки: `go-hub/third_party/qjs/runtime.go`, `go-hub/internal/hub/code_mode_runtime.go`, функция `codeModeDenyHostPolling`.

Дальнейшее измерение 20 ноября уточнило картину. На коде `origin/main` прирост на один запуск Code Mode составляет 0,220 отображения при последовательных запусках (200 прогонов) и 0,138 при параллельных (8 рабочих по 30 прогонов), то есть параллельность взрыва не даёт, и добавление сериализации инстанцирования хост-модулей результата не меняет (+53 против +47 отображений). Профиль кучи после параллельного прогона указывает на компиляцию хост-модулей движком wazevo и её трамплины. Прирост 15 ноября (12–48 отображений в минуту) в 10–40 раз выше измеренного на корабельном коде и не воспроизводится на нём: с тех пор менялся code-mode путь хаба. Наблюдение за возвратом дефекта остаётся за веткой RAM в `fleet-health` с подтверждением ядром.

Состояние на 20 ноября: корабельная линия `origin/main` не показывает накопления — у ноды на ревизии `40d08f76` за 16 минут работы ноль исполняемых отображений при 83 МиБ RSS, а producer не зафиксировал ни одного нарушения RAM за пять дней. Наблюдатель, который ловит возврат дефекта, уже существует: ветка RAM в `fleet-health` с подтверждением ядром.
